01 / The handoff

Four seats.
One bounded loop.

Each turn starts with a fresh sandbox and the exact context it needs. The host owns state, limits, retries, and writes; the agents own judgment inside their lane.

Turn noise into work.

Triage reads an incoming issue, applies only allowed labels, and routes it without touching code.

  • Constrained taxonomy. Labels come from the maintainer’s allowlist.
  • One scoped write. No closing, editing, reviewing, or pushing.
  • Issue context only. The sandbox begins empty by design.
  • Human-selected entry. Maintainers decide what moves into fixing.

Propose, prove, answer.

The fixer implements the requested change, checks it, and publishes through a broker that enforces every boundary.

  • No credentials. The agent cannot reach GitHub directly.
  • Bounded changes. File count, size, and protected-path rules are host-enforced.
  • Exact-head push. A moved branch causes a refusal, never an overwrite.
  • Answers travel forward. Every finding gets a concrete response for the next review.

Verify before verdict.

The reviewer reads the full change, runs relevant checks, and issues one evidence-backed decision.

  • Independent seat. Review runs apart from the authoring agent.
  • Evidence required. Findings include severity, command output, and source location.
  • Binary handoff. Approve, or request changes that wake the fixer.
  • No false green. A partial view can never produce approval.

End the endless round.

When the verdict budget is exhausted, the adjudicator resolves the dispute instead of buying another cycle.

  • Reads both sides. Findings and the fixer’s published answers arrive together.
  • Three rulings. Accept, reject, or respec the disputed goal.
  • Read-only workspace. The deciding seat cannot alter the change.
  • Human conclusion. Its ruling reaches the operator; it still cannot merge.

How a pull request moves

The same four seats, as a path. Read it left to right; the two notes underneath are the parts a straight line would hide.

  1. IssueA maintainer-selected issue enters the loop.
  2. →
  3. TriageLabels and routes it. Touches no code.
  4. →
  5. FixerImplements, checks, and pushes through the broker.
  6. →
  7. ReviewerApproves, or requests changes that wake the fixer.
  8. →
  9. Human mergeOnly a person merges. The loop never does.

Reviewer requests changes → back to Fixer. Each round costs a verdict, and the verdict budget caps the rounds — the loop cannot argue forever.

Budget exhausted → Adjudicator. It reads the findings and the fixer’s answers together and rules accept, reject, or respec. Its ruling reaches the operator; it still cannot merge.

CI routing depends on the PR and the settings. With fix_ci on and unattended_fixer_push on, red CI on a fixer-authored PR goes to the fixer while CI-fix capacity remains; once the budget is spent, or a CI-fix turn ends without a new head, the head is held — not reviewed, not re-sent — until the checks pass or a new head is pushed. A review-only red head is likewise held with nothing spent. With fix_ci off, or on without unattended_fixer_push, red CI on a fixer PR waits for a review instead. And where the loop posts its diaktoros/review check and the branch requires it (hermes dk protect), that check must be green before a person merges — protection itself is opt-in, not automatic.

02 / The trust boundary

Autonomy with hard edges.

Diaktoros keeps the creative work inside disposable sandboxes and the irreversible decisions inside deterministic infrastructure.

A confident answer is not proof. A clean diff is not permission. A model’s intent is not a boundary. The host verifies all three.

03 / Case study

When the agents disagree.

A real review cycle from November 2, 2026. The roles, in one line: the fixer writes the change, the reviewer independently checks it, the adjudicator ends a dispute when the verdict budget runs out, and a human merges. PR #1624 fixed a backup bug — and the reviewer nearly stopped it three times.

  1. Reviewer · round 1Nov 2, 15:21 UTC

    Vex requested changes on the first head. Finding F1 (P1, blocks): the name-only filter silently dropped real files — a legitimate artifacts/42/Cargo.lock among them — so a backup could succeed while losing data on restore. Vex proved it with a reproduction script.

    Read round 1

  2. Fixer · revision 1Nov 2, 15:31 UTC

    Drey answered every finding and pushed a fix. The nested-artifact cases were fixed; the root-level ones were not yet.

    Read the fixer’s answers

  3. Reviewer · round 2Nov 2, 15:48 UTC

    Vex requested changes again. F1 was still open: root-level lookalikes — an empty user.lock, a file named .x.abcd1234 — were still silently dropped from a successful backup.

    Read round 2

  4. Fixer · revision 2Nov 2, 15:55 UTC

    Drey answered again and pushed a second fix, with a root-level regression test that failed against the old filter and passed against the new one.

    Read the fixer’s answers

  5. Reviewer · round 3Nov 2, 16:25 UTC

    F1: fixed. But Vex still requested changes on finding F2 (P2): a first-write temp file still present at archive time was archived as litter, and two real lock files — .onboarding.lock and conflict-scan.lock — were missing from the exclusion list.

    Read round 3

  6. AdjudicatorNov 2, 16:27 UTC

    Tuck ruled ACCEPT, with all 3 verdicts counted. F2 was correct, but it did not block: the worst case was litter, not data loss or a failed backup. The dispute ended instead of buying another round.

    Read the ruling

  7. Follow-upNov 2, 17:33 UTC

    The remaining concern was not dropped. It became issue #1651 — and was since closed by PR #1710. A person merged #1624. The loop never merges.

      05 / New in v0.6.0

      Proof at every head.
      A cost for every seat.

      v0.6.0 hands the reviewer proof instead of the fixer’s word, and makes every turn earn its tokens.

      Proof at every head.

      With change_proof on, the host runs the tests a PR adds or changes before every review, in the seat’s network-less sandbox: on the merge base, where they should fail, and at the head, where they should pass. The reviewer reads the result as a fact. The seats also see the live state of every issue a PR names, and an adjudicator that rules for the fixer can approve the head itself.

      Read the v0.6.0 notes

      A cost for every seat.

      The shadow review runs by risk, GitHub reads that haven’t changed are free, and CI results and maintainer replies arrive by webhook instead of the next sweep. Give the loop your models’ prices, and hermes dk stats estimates what each seat costs, showing subscription seats at API rates beside the spend. hermes dk history replays any PR’s review cycle.

      06 / Install

      Two commands.

      From the Hermes plugin catalog — the reviewed release at its pinned commit.

      hermes plugins install diaktoros
hermes dk setup --repo "owner/repository"

      Prefer the repository? hermes plugins install coe0718/diaktoros tracks main instead.

      • Do I need Hermes first? Yes — Diaktoros is a Hermes plugin, not a standalone app.
      • What GitHub access? GitHub Apps (recommended, no personal account) or separate reader, reviewer, and fixer accounts.
      • Can I try it on one repo? Yes — hermes dk setup --repo "owner/repository" wires a single loop.
      • How much control do I keep? All of the final say: agents propose, review, and rule, but only a person merges.
      • What if a run stalls? The watchdog reports it, and a dispute at the verdict cap goes to the adjudicator instead of looping forever.
